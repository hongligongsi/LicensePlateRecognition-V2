# 待完善清单（Roadmap）

> v2.7.2 整理，v2.7.3 更新。每一项都标了**现状证据**与**建议做法**；已完成的写在文末归档区。
> 排序大致按「用户可感知收益 ÷ 实现风险」。实测依据见
> [ACCURACY.md](ACCURACY.md)。

## 一、识别与数据

### 1. 给 yolo 配 `plate_rec.onnx`（车牌专用 CRNN）⭐ 收益上界最大

* **现状**：`yolo` 定位 100/100，但 16 张失败里有 4 张仍是「有框无字」
  （通用 OCR 在低质裁剪图上放弃）。识别器与 `deep` 共用同一套通用 OCR，
  换成车牌专用 CRNN 后两边都受益。
* **上界**：v2.7.0 时是 +8 张（84%→92%）；v2.7.2 补救预处理吃掉 4 张后
  剩余上界约 **+4 张**（85%→89%）。
* **做法**：上游 we0091234 仓库只发布 `plate_rec_color.pth`（PyTorch），
  需用其 `models/` 代码导出 ONNX + `charset.txt` 放到 `models/yolo/`
  （导出坑位与 `plate_detect.pt` 相同：`weights_only=False`、外部数据内嵌）。
  推理与解码代码**已经写好**（`yolo_engine._recognize_one_crnn` / `ctc_decode`），
  权重一放就能用，`doctor` 也会提示。

### 2. 换更强的通用识别模型（PP-OCRv4/v5 server 版）

* **现状**：`deep` 与 `yolo` 共用 RapidOCR 内置识别模型；
  形近字（Z↔2、X↔4、D↔0、H↔N）是当前最大的失败类（8/15）。
* **做法**：仓库已有 `models/ch_PP-OCRv4_rec_mobile.onnx`（未入库），
  实测作为**失败补救**是零收益（[ACCURACY.md §5.1](ACCURACY.md)）；
  换成 server 版并作为**主**识别模型是一条没试过的路，需实验，
  代价约 3~4 倍识别耗时。

### 3. 特殊牌专用成员接入 fusion

* **现状**：特殊牌（港/警/领/学/双层）自有样张上 `deep` 10/10、`yolo` 8/10，
  而 CCPD 几乎不覆盖这些形态 —— 这是两套数据排名反转的全部原因，
  也是 fusion 目前**唯一可能的互补方向**（当前 deep 命中集是 yolo 的子集，
  互补收益为 0）。
* **做法**：给 fusion 加「版式分类 → 选成员」路由（yolo 检测头本来就能
  输出单/双层类别），或攒特殊牌数据后微调。**不要**在 11 张样张上调参。

### 4. 样张目录治理（v2.7.3 起优先级提高）⭐ 已经让 CI 变红

* **现状**：仓库根有两个"样张"目录，都已经跑偏：
  * `img/` 原本只有 9 张入库样张，现在里面有 **202 个文件（55MB）**，其中
    192 个既不在 git 里、也不在回归基线里（10-13 与 10-16 两天各涌入约 90 张，
    文件名是哈希式的 `.jpg/.jpeg/.webp`）。后果：`test_baseline_covers_repo_samples`
    与"样张总体积 < 40MB"两条测试实测变红（61.4MB）；
  * `images/`（.gitignore 里的"集中副本"）现在是**空目录**。
* **为什么不能靠"重新生成基线"糊过去**：把 192 张随手抓来的图写进基线，
  等于让 CI 每次 checkout 多下 50MB、每次跑测试多算 190 张图的定位，
  而这些图根本不是"项目承诺保持稳定"的那批。
* **做法**（需要先决定目标，再动手）：
  1. 若这些图只是本地试验数据 → 把 `img/` 恢复成入库的那 9 张（git 里有），
     其余挪到 `datasets/local/`（已 gitignore）；
  2. 若确实要长期保留 → 样张移出仓库（或用 git-lfs），
     基线只覆盖一个显式的清单文件，而不是"目录里有什么就测什么"；
  3. 无论选哪条，`tests/baselines/real_samples.json` 与 3 个测试文件里的路径引用要一次改齐。
* **注意**：`make_regression_baseline.py` 的样张来源是 `SAMPLE_DIRS = ("img", "samples")`
  这种"扫目录"写法，目录一被污染基线就跟着变 —— 这也是上面第 2 条建议的理由。

### 4b. 运行日志的后续（v2.7.3 之后）

* **现状**：日志已落盘（含多进程按 pid 分文件），但**界面面板只读内存缓冲**，
  不读文件；`--workers` 模式下一次运行会产生 1 + N 个文件，没有聚合视图。
* **做法**：
  * 面板加一个「查看文件」入口（把当天的主日志读进来，或直接交给系统默认程序打开）；
  * 可选：子进程日志在父进程收尾时合并成一份 `lpr-<日期>-all.log`（注意并发写入）；
  * 明确**不做**自动上报：车牌识别涉及个人数据，日志只留本地。

### 4c. 日志里的"运行环境指纹"

* **现状**：排查"同一张图昨天能认、今天认不出"时，日志里没有版本/后端/配置指纹，
  只有引擎就绪那一行（`后端=rapidocr | 定位引导=启用 …`）。
* **做法**：启动时记一条 `lpr <版本> | Python <版本> | OpenCV <版本> | 引擎默认=<x> |
  关键阈值=<hash>`，一行就够 —— 让"配置/环境变了"与"算法变了"可区分。

### 5. 二次识别实验：让第二模型始终参与投票

* **现状**：`secondary_rec_model` 只在"主模型零产出"时激活（§5.1 实测零收益）。
  形近字失败是"高置信度地读错"，恰恰绕过了这条触发线。
* **做法**：实验性地让第二模型**始终**计一票（票权打折），看形近字 8 张里
  能不能靠两模型分歧救回。风险：错误模式高度相关（同为 PP-OCR 系），
  收益可能仍为 0 —— 所以是实验，不是承诺。

### 5b. 补救预处理做成可配置开关

* **现状**：v2.7.2 起补救预处理是默认行为。`deep` 用户要为它付约 30% 的
  耗时（716→946 ms/张，中位数），而 `deep` 的实测识别收益是 0 张。
* **做法**：加 `engine.rescue_preprocess: bool = True`（或 `off/auto/deep,yolo`
  三态），吞吐敏感的场景可以关。改动很小：`_recognize_candidates` 的触发
  条件再与配置求与即可。

## 二、工程与发布

### 6. `start.sh`（Linux / macOS 启动壳）

* **现状**：`tools/launcher.py` 本身跨平台（`venv_python()` 已区分
  `Scripts/` 与 `bin/`），缺的只是一个 shell 引导壳。v2.7.1 用户只要了
  Windows 侧的自检。
* **做法**：仿照 `start.bat` 的两层结构（纯 POSIX sh 引导 + Python 打印中文）。

### 7. 权重获取体验

* **现状**：`yolo` 权重不入库（体积 + 许可），用户装完 extras 后必然看到
  「（不可用）」。`doctor` 会打印确切命令，但用户仍要手动跑
  `tools/fetch_yolo_weights.py`。
* **做法**：明确**不做**无确认的自动下载（许可与哈希可信链要求），
  但可以在 `doctor` 里加一个交互式「现在下载吗？（y/N）」。

### 8. `annotated/`、`out/` 目录的定位

* **现状**：两个目录都在仓库根，README 没解释它们是谁写的、能否删。
* **做法**：要么在 README 的目录表里注明，要么挪进 `reports/`（已 gitignore）。

## 三、界面（本轮已完成的部分之外）

### 9. 摄像头连续识别模式下的候选表刷新

* **现状**：v2.7.2 的候选表只对静态图片批量显示，摄像头模式下每帧都会
  重置（3fps 下可见轻微闪烁，未做节流）。
* **做法**：候选表内容与上一帧相同时跳过重绘。

### 10. 历史记录持久化

* **现状**：识别历史只在内存里，关窗即失（CSV 导出是手动动作）。
* **做法**：可选的本地 SQLite/JSONL 落盘 + 启动时恢复，注意隐私策略
  （`mask_output` 打开时不能落明文）。
