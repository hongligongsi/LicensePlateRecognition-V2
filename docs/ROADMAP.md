## 一、识别与数据

### 1. 给 yolo 配 `plate_rec.onnx`（车牌专用 CRNN）⭐ 收益上界最大

* **现状**：`yolo` 定位 100/100（[§2.1](ACCURACY.md)），但 11 张失败里仍有 4 张是
  「有框无字」（blur 2 / db 1 / challenge 1，通用 OCR 在低质裁剪图上直接放弃输出）。
  识别器与 `deep` 共用同一套通用 OCR，换成车牌专用 CRNN 后两边都受益。
* **上界**：v2.7.0 时是 +8 张（84%→92%）；v2.7.2 补救预处理吃掉 4 张，上界落在 +4；
  v2.8.0 识别计划又救回 4 张（85→89），**剩余上界仍是 +4 张（89%→93%）** ——
  这次要救的是「零输出」的图，不是「读错」的图。⚠️ 其中 `0131_039` / `0162_049`
  连 `deep` 也读不出，实际能救回几张未知。
* **做法**：上游 we0091234 仓库只发布 `plate_rec_color.pth`（PyTorch），
  需用其 `models/` 代码导出 ONNX + `charset.txt` 放到 `models/yolo/`
  （导出坑位与 `plate_detect.pt` 相同：`weights_only=False`、外部数据内嵌）。
  推理与解码代码**已经写好**（`yolo_engine._recognize_one_crnn` / `ctc_decode`），
  权重一放就能用，`doctor` 也会提示。

### 2. 换更强的通用识别模型（PP-OCRv4/v5 server 版）

* **现状**：`deep` 与 `yolo` 共用 RapidOCR 内置识别模型；
  形近字（Z↔2、X↔4、D↔0、H↔N、A↔4）是当前最大的失败类
  （`yolo` 11 张失败里 5 张、`deep` 21 张里 8 张）。
* **做法**：仓库已有 `models/ch_PP-OCRv4_rec_mobile.onnx`（未入库），
  实测作为**失败补救**是零收益（[ACCURACY.md §5.1](ACCURACY.md)）；
  换成 server 版并作为**主**识别模型是一条没试过的路，需实验，
  代价约 3~4 倍识别耗时。

### 3. 特殊牌专用成员接入 fusion

* **现状**：特殊牌（港/警/领/学/双层）自有样张上 `deep` 10/10、`yolo` 8/10，
  而 CCPD 几乎不覆盖这些形态 —— 这是两套数据排名反转的全部原因，
  也是 fusion 目前**唯一可能的互补方向**（当前 deep 命中集是 yolo 的子集，
  互补收益为 0）。
* **做法**：给 fusion 加「版式分类 → 选成员」路由（yolo 检测头本来就能
  输出单/双层类别），或攒特殊牌数据后微调。**不要**在样张上调参 ——
  仓库里那 400 多张图**带人工真值的只有 11 张**，没有真值就调不了参。

### 4. 样张目录治理 —— **已决定：保留入库、改门槛**（2026-10-16），但根因未除

* **决定**（使用者拍的板）：`img/` 里的图**全部保留在仓库**，不动数据；
  随之把两条守卫改成如实反映现实：
  * `tests/baselines/real_samples.json` 重新生成：**11 条 → 403 条**
    （`img/` 401 + `samples/` 2；`img/` 里的 `A1_Z拖链.3mf` 不是图片，
    被 `collect()` 按扩展名滤掉）；
  * 体积预算 `40MB → 150MB`（`tests/test_regression_baseline.py::SAMPLE_SIZE_BUDGET_MB`）。
    **这等于承认该断言退化成"失控增长护栏"**，不再是"体积小 / checkout 很快"的承诺。
* **执行时的真实数据**：`img/` 402 个文件（401 张图 + 1 个 3mf）68.8MB，
  连同 `samples/` 的 2 张，**样张总体积 75.7MB**。
* **⚠️ 根因订正（v2.8.1 查证）**：此前记的「重命名丢了 CCPD 原始文件名（含 bbox 真值）」
  **不准确**。`tools/fetch_ccpd.py` 下载的是 ModelScope 镜像上的
  `sample/image/sample_{i}.jpg` —— **镜像本身就用这个文件名**，原始 CCPD 文件名在源头
  就没有了，不是我们改名弄丢的。所以「再下载时保留原始文件名」这条**走不通**；
  想扩真值只有两条路：① 沿用 `datasets/ccpd_labeled/_labels.json` 那套（含 `orig`
  原始名）的来源继续标；② 人工标。详见 [ACCURACY.md §8](ACCURACY.md) 的样本量局限。
* **仍存在的根因（真正要盯的）**：`img/` 同时是**下载样本的落图目录** ——
  `tools/fetch_ccpd.py` 下到 `datasets/ccpd_raw`（已 gitignore），之后被搬进 `img/`。
  当天就有 17:18、17:26、18:25 三批涌入（最后一批 200 张 `sample_*.jpg`，索引到 1177），
  而 `datasets/ccpd_raw` 里还躺着 654 个文件。只要这个用法继续，
  **每加一批图就得重新生成基线，体积预算也会很快过时**（75.7MB 距 150MB 只剩一倍）。
* **建议的根治办法**（留待后续，任选其一）：
  1. 下载样本就在 `datasets/` 里评测，不要搬进 `img/`（这是 .gitignore 字面上的意图）；
  2. 若必须入库，把基线来源从"扫目录"改成**显式清单文件** ——
     `make_regression_baseline.py` 现在是 `SAMPLE_DIRS = ("img", "samples")`，
     "目录里有什么就测什么"，目录一被污染基线就跟着变；
  3. 体积回到 40MB 量级后，把 `SAMPLE_SIZE_BUDGET_MB` 改回去。
* **顺带澄清**：`images/`（.gitignore 里的"集中副本"）现在**是空目录**，
  原先"`img/` 是 `images/` 的严格子集"的说法已不成立，README §15.4 与 §3.7 已一并改掉。

### 4b. 运行日志的后续（v2.7.3 之后）

  * 明确**不做**自动上报：车牌识别涉及个人数据，日志只留本地。

### 5. 二次识别实验：让第二模型始终参与投票

* **现状**：`secondary_rec_model` 只在"主模型零产出"时激活（§5.1 实测零收益）。
  形近字失败是"高置信度地读错"，恰恰绕过了这条触发线。
* **做法**：实验性地让第二模型**始终**计一票（票权打折），看形近字那 5~8 张里
  能不能靠两模型分歧救回。风险：错误模式高度相关（同为 PP-OCR 系），
  收益可能仍为 0 —— 所以是实验，不是承诺。

### 5b. 补救预处理做成可配置开关 —— ✅ 已完成（v2.8.1）

> 实装为 `engine.rescue_preprocess: bool = True`，默认保持 v2.7.2 起的行为。
> 注意它是**引擎级**而不是 `deep` 专属：`yolo` 复用同一条识别管线。
> 保留原文备查：

* **现状**：v2.7.2 起补救预处理是默认行为。`deep` 用户要为它付约 30% 的
  耗时（716→991 ms/张，中位数；v2.7.2 当次实测是 716→946），
  而 `deep` 的实测识别收益是 0 张。
* **做法**：加 `engine.rescue_preprocess: bool = True`（或 `off/auto/deep,yolo`
  三态），吞吐敏感的场景可以关。改动很小：`_recognize_candidates` 的触发
  条件再与配置求与即可。
